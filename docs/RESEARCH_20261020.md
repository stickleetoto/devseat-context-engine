# Research memo — CPU-first evidence-aware context compression (2026-10-20)

## Research sources and transfer

1. **LLMLingua** (EMNLP 2023) proposes coarse-to-fine prompt compression, budget control, and iterative token scoring. We adopt the need for budgeted evaluation, not its code or model. https://aclanthology.org/2023.emnlp-main.825/
2. **LongLLMLingua** (ACL 2024) considers question-aware compression of long contexts; motivates query-linked fragment ranking. https://www.microsoft.com/en-us/research/project/llmlingua/publications/
3. **LLMLingua-2** (Findings of ACL 2024) approaches faithful compression as extractive token classification with a smaller bidirectional model. It motivates provenance-aligned extraction; our method is regex/lexical only and **does not reproduce model results**. https://aclanthology.org/2024.findings-acl.57/
4. **Lost in the Middle** (TACL 2024) shows that long-context use can be sensitive to position. Motivates position-stratified downstream evaluation. https://aclanthology.org/2024.tacl-1.9/

## Technology implemented in v0.3

- **Span-level compression:** split prose by punctuation, keeping exact original Python string character offsets.
- **Atomic evidence:** keep fenced code blocks and Python traceback blocks together; do not split their internal lines.
- **Query relevance:** transparent lexical overlap with Hangul bigrams, plus a small neighboring-fragment bonus.
- **Hard literals:** a trusted caller can require exact substrings. Merge overlapping sentence units before selection; fail if mandatory units exceed budget. Never generate replacements.
- **Provenance:** every selected fragment is an exact source substring. Validate source alignment programmatically.
- **Evaluation:** manually annotated exact answer literals are withheld from the compressor during the benchmark. Compare v0.2 paragraph-level and v0.3 span-level selection under identical character budgets.

## Synthetic benchmark (4 scenarios, 7 annotated literals)

- v0.2 paragraph baseline: 4/7 retained = 57.1%.
- v0.3 document-span candidate: 6/7 retained = 85.7%.
- Test cases: Korean authentication incident, English service failure, Python traceback, payment order ID.
- These hand-made cases are **not representative**, and character reduction is not model-token savings. No statistically sound generalization or downstream answer-correctness claim follows.

## Limitations, safety and failure modes

- No semantic compression, learned embeddings, semantic entailment, contradiction resolution, guarantee against prompt injection, or downstream LLM success validation.
- Exact-source extraction does not imply faithful meaning: e.g. dropping "updated" evidence can leave a stale amount.
- Sentence splitting is heuristic; markdown, URLs, abbreviations, international punctuation, unicode normalization and partial code fences need harder tests.
- Literal requirements only cover exact character spans. Underlying trust classification is a caller's responsibility; do not derive mandatory status from an external document saying "IMPORTANT".
- Small fragments cause non-additive tokenization and potentially O(n²) whole-output recounting. The default token estimator is rough; strict production budgets need provider-specific tokenizers and message envelope reservations.
- No logging of private prompt text is performed by the library; integrators should protect query/source/trace data.

## Validation gates before general release

1. 100+ held-out Korean, English, code, log, mixed-language contexts including contradictions and negative evidence.
2. Measured answer accuracy using at least two downstream LLMs; compare literal recall separately from semantic correctness.
3. Exact tokenizer integrations and total message/window envelope accounting.
4. CPU latency p50/p95 at 1k, 10k and 50k span sizes.
5. Signed/structured provenance with BIO memory and Agent Harness, no cross-tenant scope leaks.
